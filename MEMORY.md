# Memory

- This repository owns reusable OpenShell base images, workspace/Git lifecycle behavior, shared policies, gateway operations, and client isolation conventions.
- Client permissions remain separate. The initial Pi client consumes reviewed Pi-owned assets from `pi-customizations`; settings/session translation, OAuth compatibility, provider profile, resources, and the entrypoint remain owned there.
- API version 1 is the hook contract used by `openshell-workspace`: `prepare`, `upload`, `download`, and `exec-env` phases.
- Images use full local references under `localhost/openshell-environments` and explicit version tags. Launch never builds implicitly; `bin/openshell-image` owns deliberate build, inspection, and cleanup.
- The base intentionally tracks current Terraform, uv, Ruff, and Rust images; Node major 24 and Debian trixie are explicit. Pin tool images in a project branch when exact reproducibility is needed.
- General web policy allows only public global-unicast addresses on ports 80/443. Client provider profiles remain narrower and client-owned.
- Portable Pi releases use three schema-versioned contracts under `contracts/`: sanitized assets, host integration, and release compatibility. Contract/API version 1 requires exact SHA-256 checksums, committed source revisions, safe allowlisted paths, and a GHCR version tag paired with an immutable digest.
- Pi asset and host package archives are deterministic tar.gz files. Stable releases require `SHA256SUMS`, GitHub artifact attestations, and keyless Sigstore signing of the OCI digest; secrets, state, broad settings, links, traversal, caches, and checkout-relative runtime paths are forbidden. A host archive cannot embed its own checksum, so its `compatibility.json` omits that field and external `SHA256SUMS`/provenance bind the completed archive.
- The portable package installs under XDG data directories and resolves runtime files relative to itself. Local checkout paths and mutable images are explicit development overrides only. The current Dockerfile's whole committed-tree build remains the 0.1.0 rollback baseline until Phase 3 switches image inputs.
- Phase 2 is implemented in `pi-customizations`: its clean-tree exporter uses exact mappings to produce deterministic, reopened/verified asset and host archives; host export validates supplied release metadata and the selected asset archive identity. Exports do not install, publish, or activate packages.
- OpenShell's Pi execution environment can replace the image `PATH` and omit image `RUSTUP_HOME`/`CARGO_HOME`, while the Pi home is read-only. The base image provides `/usr/local/bin` Rust wrappers that restore those variables before delegating to rustup shims; the Pi image also starts through a toolchain wrapper which exports the Rust path/state before Pi starts, ensuring its child shell commands inherit it. `openshell-image build pi/all` runs Cargo, Rustc, Rustfmt, and Clippy through the Pi entrypoint under that restricted environment and fails the build if any are unavailable.
- Phase 3 is complete: the Pi image (`0.2.0`) no longer bakes the whole `pi-customizations` checkout into `/opt/pi-customizations`. `bin/openshell-image build pi` now runs `pi-customizations/bin/export-pi-release.mjs assets` to produce the sanitized `pi-assets-<version>.tar.gz`, and only that archive enters the Docker build context; `/opt/pi-customizations` keeps just the archive's `manifest.json` as a read-only audit record. Pi auto-discovers `agents`, `extensions`, `skills`, `themes`, and `APPEND_SYSTEM.md` directly from `$PI_CODING_AGENT_DIR` (`dist/core/resource-loader.js`'s default resource roots, verified against the shipped npm package) with no `settings.json` registration required, so the image installs those under `/home/pi/.pi/agent/...` and no longer generates a `settings.json` at build time.
- `bin/openshell-image build pi/all` accepts `--pi-source PATH` (local checkout, a development override) or `--pi-ref REF` (shallow `git fetch --depth 1` of a tag/branch/SHA straight from `https://github.com/enriqTS/pi-customizations`, no local checkout needed) — exactly one is required. This lets a machine with no `pi-customizations` checkout still build the image, moving closer to the top-level portability objective even for local/manual builds, not just CI. The prior whole-tree-copy build remains reachable at git tag `v0.1.0` as the rollback baseline.
- Phase 4 is complete: rather than having this repo's CI clone `pi-customizations`' source and run its exporter, `pi-customizations` publishes its own `pi-assets-<version>.tar.gz` as a GitHub Release (tag `pi-assets-v<version>`, its own independent version line) via `.github/workflows/release-pi-assets.yml`, with `SHA256SUMS` and a build-provenance attestation on the archive. `bin/openshell-image build pi` gained a third source mode, `--pi-assets-version VERSION`, which only downloads and checksum-verifies that published archive — never a git clone or running another repo's scripts. `clients/pi/pi-assets.version` pins which release this repo's build consumes; bumping it is a small, reviewable commit, done before cutting a new environment release. `.github/workflows/release-images.yml` (tag `v<semver>` matching `VERSION`) builds `base` then `pi` (pinned to `base`'s pushed digest), pushes both to `ghcr.io/enriqts/openshell-environments/{base,pi}` with a BuildKit SBOM/provenance attestation, signs both keylessly with `cosign` over GitHub Actions OIDC, then a `verify-clean-pull` job with **no checkout step at all** pulls both by digest and reruns the resource-layout and restricted-PATH Rust checks — proving a machine with neither source repository present can pull and launch them. Only `linux/amd64` is published; this session's sandbox and GitHub-hosted runners can only build and test that architecture, so broader platform support is never claimed unverified.
- When one repository's CI depends on another repository's build output, the established preference (confirmed with the user while designing this) is for the producing repository to publish its own versioned, checksummed release artifact for the consumer to download and verify, rather than the consumer cloning the producer's source and invoking its build scripts directly — it keeps each repository responsible for building and vouching for its own output.
- `ghcr.io/enriqTS/...` (the GitHub username's real casing, used throughout the original `PLAN.md` and Phase 1 contracts) is an invalid OCI image reference: Docker/OCI repository names must be all-lowercase. This only surfaced on the first real `docker push` to GHCR (`docker tag` fails immediately with "must be lowercase" and is the fastest local way to check a candidate reference). The fix is `ghcr.io/enriqts/...`; GHCR maps the lowercase image path to the `enriqTS` account regardless of the username's real casing. GitHub source/clone URLs (`https://github.com/enriqTS/...`) are a completely different thing and are unaffected — don't conflate the two when auditing for this.
- `0.2.0` and `pi-assets-v0.1.0` are genuinely published: `ghcr.io/enriqts/openshell-environments/{base,pi}:0.2.0` and https://github.com/enriqTS/pi-customizations/releases/tag/pi-assets-v0.1.0. Both were independently pulled and `cosign verify`'d from outside CI after the fact, not just trusted from the workflow's own success report.
- The `pi-customizations` checkout on this machine has, at least once, had its local `main` branch pointer quietly move backward to an earlier commit between one git operation and the next (a commit that was already successfully pushed vanished from local `HEAD`'s ancestry, discovered only because a later push was rejected as diverged). Cause unconfirmed — this repo's own memory documents that an active OpenShell Pi sandbox snapshots and can overwrite this exact checkout on sync, which is the leading suspect. Nothing was actually lost since the commit was already on `origin`, and `git rebase origin/main` cleanly reconciled it, but always re-run `git log --oneline --parents` / compare against `origin` right before trusting local history in this checkout, rather than assuming a prior commit is still there.
